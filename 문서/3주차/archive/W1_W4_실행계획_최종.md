# AI 파트 W1~W4 실행계획 (중간발표 2026-04-17)

> 기준일: 2026-03-21(토)
> 중간발표: 2026-04-17(금)

---

## 0. 왜 이렇게 나누는가

우리 AI 파트의 핵심 구조는 **5-agent 파이프라인**이다.

Data → Strategy → Risk → Backtest → Final Decision

이 파이프라인에서 **입구(Data)와 출구(Risk → Final Decision)** 를 한 사람이 잡고, **중간 엔진(Strategy → Backtest)** 을 한 사람이 잡으면, 서로의 작업이 겹치지 않으면서도 artifact 기반으로 정확히 연결된다.

구체적으로:

- **AI #1** 이 만든 DailyMarketPacket + TickerTextPack을 **AI #2** 가 받아서 전략을 만든다
- **AI #2** 가 만든 StrategyCard를 **AI #1** 이 받아서 리스크를 적용하고 최종 판단을 내린다
- **AI #2** 가 만든 BacktestReport를 **AI #1** 이 참조해서 Final Decision의 신뢰도를 판단한다

즉 **AI #1 → AI #2 → AI #1** 순서로 데이터가 흐르기 때문에, 둘의 작업이 직렬이 아니라 **교차 의존** 관계다. 이게 역할을 명확히 나눠야 하는 이유다.

## 1. 역할 분담 근거

### AI #1 (장재원): Data Agent + Risk Agent + Final Decision Agent + UQ calibration

**왜 이 조합인가:**

① **Data Agent와 Final Decision Agent는 파이프라인의 양 끝**이다. 한 사람이 입구와 출구를 동시에 잡으면 전체 데이터 흐름을 통제할 수 있고, "입력에 문제가 있어서 출력이 이상하다" 같은 E2E 디버깅이 빠르다.

② **Risk Agent는 규칙 기반**이다. ML 모델 학습이 아니라 정책(position cap, stress gate, uncertainty tail cap)을 설계하고 적용하는 거라서, Data Agent의 시장 데이터를 직접 다루는 사람이 맡는 게 자연스럽다. Risk가 참조하는 market_stress, volatility 같은 값도 Data Agent가 만든다.

③ **Final Decision Agent는 Kanana-o를 사용**한다. Kanana-o 접근권을 가진 사람이 prompt engineering, fallback 로직, explanation 생성을 직접 관리하는 게 효율적이다.

④ **UQ calibration**은 Risk Agent의 P85 uncertainty tail cap을 위한 threshold를 잡는 작업이다. Risk Agent를 만드는 사람이 uncertainty threshold도 직접 튜닝해야 정책과 모델이 일관된다.

**핵심 키워드: online serving + governance + 파이프라인 양 끝 통제**

### AI #2 (팀원): Strategy Agent (Quant + News + Synthesizer) + Backtest Agent

**왜 이 조합인가:**

① **Quant Strategy가 이 프로젝트의 ML 핵심**이다. LightGBM ranker 학습, feature engineering (manual → MLF-lite → UMI-lite), cross-sectional ranking label 설계가 전부 여기에 있다. ML 모델 학습과 실험을 한 사람이 집중해서 맡는 게 품질이 높아진다.

② **News/Market Strategy도 Strategy Agent 안에 있다.** Quant으로 shortlist를 만들고, 그 shortlist에 대해서만 LLM 뉴스 해석을 하는 구조라서, shortlist를 만드는 사람이 뉴스 해석도 같이 다루는 게 맞다. "왜 이 종목이 shortlist에 들어갔는데 뉴스는 부정적인가?" 같은 conflict를 General Synthesizer에서 해소해야 하기 때문이다.

③ **Backtest Agent는 Strategy의 검증 도구**다. 전략을 만든 사람이 직접 검증해야 "이 전략이 왜 안 됐는지"를 가장 빠르게 파악하고 개선할 수 있다. walk-forward, purge/embargo, baseline 비교, failure 분석까지 전부 전략 품질과 직결된다.

④ **UQModel도 Backtest 안에서 학습**된다. historical data로 uncertainty score를 산출하고 calibration하는 건 offline 실험이라서, Backtest를 돌리는 사람이 같이 하는 게 효율적이다. (다만 운영 책임은 AI #1이 가진다.)

**핵심 키워드: offline modeling + validation + ML 핵심 엔진**

## 2. Producer/Consumer 관계

이 구조가 작동하려면 **누가 무엇을 만들고 누가 소비하는지**가 명확해야 한다.

- **DailyMarketPacket**: AI #1이 만든다 → AI #2가 받아서 feature 계산에 사용
- **TickerTextPack**: AI #1이 만든다 → AI #2가 받아서 News Strategy에 사용
- **QuantShortlist**: AI #2가 만든다 → AI #2 내부에서 News Strategy 대상 결정에 사용
- **StrategyCard**: AI #2가 만든다 → AI #1이 받아서 Risk 적용 + Final Decision에 사용
- **UQModel**: AI #2가 offline 학습한다 → AI #1이 online inference에 사용
- **RiskCard + CandidateOrderPlan**: AI #1이 만든다 → AI #1 내부 Final Decision에 사용
- **BacktestReport + FailureCaseCard**: AI #2가 만든다 → AI #1이 Final Decision 신뢰도 판단에 참조
- **FinalDecisionCard**: AI #1이 만든다 → Service Layer로 전달

**핵심**: AI #1과 AI #2 사이의 인터페이스는 딱 4개다.
→ DailyMarketPacket, TickerTextPack (AI #1 → AI #2)
→ StrategyCard, UQModel (AI #2 → AI #1)

이 4개의 JSON schema만 W1에 합의하면, 이후에는 각자 독립적으로 개발할 수 있다.

## 3. W1~W4 주차별 계획

**이 주의 목표**: 서로가 주고받을 artifact의 형태를 확정하고, 각자 개발 환경을 세팅한다.

- DailyMarketPacket, TickerTextPack, RiskCard, FinalDecisionCard 스키마 v1 작성
- Risk 정책 YAML v0 작성 (position cap 20%, stop-loss -5%, turnover cap 30%, cash 10%, stress gate 3단계)
- Final Decision prompt contract v0 작성 (can_change_weight = false 명시)
- UQ 모델 I/O spec 작성 → **AI #2와 합의**
- Kanana-o 접근권 확인 + 첫 API 호출 테스트

**AI #2 태스크:**
- 학습 라벨 확정: 5거래일 forward excess return rank
- StrategyCard, QuantShortlist 스키마 v1 작성
- manual factor 목록 확정 (mom_5d/20d/60d, vol_20d, adv_20d, rsi_14, macd, macro 3종)
- LightGBM 환경 세팅 + 라이브러리 설치
- Backtest protocol v0 작성 (walk-forward 방식, fee/slippage 설정, baseline 목록)
- historical OHLCV 데이터 수집 시작 (2015~)

**공동 작업:**
- artifact schema 리뷰 + **4개 인터페이스 JSON 합의** (DailyMarketPacket, TickerTextPack, StrategyCard, UQModel I/O)

**W1 종료 기준**: 모든 artifact JSON 예시가 생성되고, 두 사람이 동일 스키마에 합의 완료

## 5. W1~W4에서 하지 않을 것

이걸 명확히 빼야 프로젝트가 안 무너진다.

- **Similar Case Retriever full 구현** → W9 이후 또는 선택 확장
- **related_company_docs 동적 자동 생성** → 중간발표 전 제외 (static mapping이면 허용)
- **xLSTM / PatchTST shadow baseline** → LightGBM 안정화 후
- **full GNN relation encoder** → 이번 학기 선택 확장
- **anonymization ablation** → W8 이후 optional
- **UMI-lite full reproduction** → Phase 3에서 stress/synchronism 일부만
- **MLF-lite** → Phase 2 (W5~W8)에서 추가, Phase 1은 manual factors만

## 7. UQ Calibration — 이건 어떻게 협업하는가

UQ는 AI #1과 AI #2가 함께 다루는 cross-cutting 모듈이다. ownership이 애매하면 W6쯤에 충돌나니까, 지금 명확히 정한다.

**AI #2가 하는 것:**
- Backtest 과정에서 historical uncertainty score 산출
- 재보정 실험 (calibration curve, reliability diagram)
- UQModel 파일 생성 → AI #1에 전달

**AI #1이 하는 것:**
- P85 threshold 결정 (어디서 자를지)
- tail-cap policy 설계 (P85 초과 시 비중 × 0.5)
- online inference (매일 StrategyCard 받으면 uncertainty_score 산출)
- Risk Agent에 통합

**한 줄 정리**: AI #2가 모델을 만들고, AI #1이 정책을 만든다.

## 8. 중간발표에서 우리가 보여줘야 하는 것

중간발표 목표는 **성능 시연이 아니다**. "5-agent 시스템이 artifact 기반으로 실제 돌기 시작했다"를 보여주는 것이다.

**데모 시나리오 (1일 추천 흐름):**

① Data Agent가 2026년 3월 X일 시장 데이터를 수집했다
→ DailyMarketPacket + TickerTextPack 보여줌

② Strategy Agent가 LightGBM으로 Top 5 종목을 뽑고, 뉴스를 해석했다
→ QuantShortlist + StrategyCard 보여줌

③ Risk Agent가 stress gate green 확인, 삼성전자 uncertainty P72 (통과), 카카오 uncertainty P88 (tail cap 적용)
→ RiskCard + CandidateOrderPlan 보여줌

④ Final Decision Agent가 삼성전자 BUY 승인, 카카오 HOLD 판정
→ FinalDecisionCard 보여줌 (Kanana-o가 생성한 한국어 설명)

⑤ Backtest 결과: 최근 20거래일 기준 KOSPI200 대비 +X%, equal-weight 대비 +Y%
→ BacktestReport 보여줌

이 흐름이 **끊기지 않고 연결되어 있다**는 걸 보여주면 중간발표는 성공이다.
