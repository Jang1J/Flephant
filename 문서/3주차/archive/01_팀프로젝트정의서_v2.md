# 팀 내부 공유용 프로젝트 정의서 v2

> 목적: 팀원 전원이 **같은 프로젝트를 상상하도록** 만드는 기준 문서.  
> 이 문서는 “우리가 무엇을 만들고 / 무엇을 만들지 않으며 / 어떤 순서로 확장하는지”를 고정한다.

---

## 0. 이 프로젝트를 가장 짧게 설명하면

**미국 DOW30 일봉 유니버스에서 장마감 시점의 가격·기술팩터·뉴스를 수집하고, Strategy Agent가 정량 prefilter와 분석 모듈을 통해 투자 thesis를 구조화된 카드로 생성하면, Risk Agent가 이를 실행 가능한 주문으로 바꾸고, Backtest Agent가 T+1 open 기준으로 검증 및 실패사례를 발행해 다시 전략을 교정하는 SOP 기반 금융 멀티에이전트 시스템을 만든다.**

---

## 1. 이 프로젝트의 본질

### 1.1 우리가 만드는 것

우리가 만드는 것은 아래 셋을 동시에 만족하는 시스템이다.

1. **트레이딩 시스템**이다.  
   단일 예측 모델이 아니라 데이터 수집부터 검증까지 이어지는 end-to-end workflow다.

2. **멀티에이전트 시스템**이다.  
   하나의 모델이 모든 결정을 혼자 하는 구조가 아니라, 역할이 다른 4개 에이전트가 순차적으로 협업한다.

3. **연구 인프라**다.  
   단순히 “돌아가는 제품”이 아니라, 어떤 계층이 성능과 리스크에 기여했는지 실험 가능한 형태로 설계한다.

### 1.2 우리가 만드는 것이 아닌 것

아래는 이 프로젝트의 목표가 아니다.

- MetaGPT 프레임워크를 그대로 복제하는 것
- TradExpert의 모든 Expert LLM을 LoRA fine-tuning으로 재현하는 것
- AAPM 전체를 asset pricing 논문 수준으로 재현하는 것
- AlphaGAT/AlphaAgent/R&D-Agent-Quant를 full reproduction하는 것
- 모든 모델을 처음부터 직접 pretrain/fine-tune하는 것
- 전 종목 full LLM ranking 시스템을 만드는 것
- 고빈도 트레이딩 시스템을 만드는 것

### 1.3 팀원 모두가 기억해야 하는 핵심 문장

> **목표는 트레이딩 시스템이고, 에이전트 구조는 그 시스템을 설계하는 방식이다.**

## 2. 현재 프로젝트의 최종 골격

## 2.1 프로젝트 층위

현재 프로젝트는 크게 **두 개의 루프**로 이해하면 가장 정확하다.

### A. Runtime Trading Loop (이번 학기 코어)

```text
Data -> Strategy -> Risk -> Backtest -> Feedback -> Strategy
```

이 루프가 실제 매일 돌아가는 트레이딩 의사결정 파이프라인이다.

### B. Offline Research Loop (확장/후속연구)

```text
가설 생성 -> 팩터/모델 제안 -> 구현 -> 실험 -> 분석 -> 다음 탐색 방향 선택
```

이 루프는 R&D-Agent-Quant, AlphaAgent, AlphaGAT 같은 논문에서 영감을 받은 **연구개발 루프**다.  
이번 학기에는 Runtime Loop가 우선이고, Offline Loop는 설계 철학이나 1차 확장으로만 반영한다.

## 3. 고정 전제 (팀 내 불변 규칙)

## 3.1 시장 / 빈도 / 유니버스

| 항목 | 고정안 |
|---|---|
| 시장 | 미국 주식 |
| 빈도 | 일봉 |
| 유니버스 | **2020-01-01 기준 고정 DOW30** |
| 종목 선택 | DOW30 전체 -> Quant Prefilter -> shortlist 5~8개 |

## 3.2 정보 시계(clock) / 누수 방지

| 항목 | 고정안 |
|---|---|
| 정보 스냅샷 시점 | **T일 16:00 ET** |
| 사용 가능 뉴스 | `timestamp <= T일 16:00 ET` |
| 16:00 이후 기사 | **T+1 정보셋으로 이월** |
| 사용 가격 정보 | T일까지의 OHLCV + 기술팩터 |
| 집행 시점 | **T+1 open** |
| 거래비용 | 편도 10bp slippage + 수수료 |
| 검증 방식 | walk-forward 최소 3-fold |

## 3.3 해석상 제한

- 상용 LLM의 사전학습 지식으로 인한 잠재적 정보누수를 완전히 제거하지 못할 수 있다.
- 따라서 결과는 strict asset-pricing claim보다 **architecture ablation + engineering evaluation** 중심으로 해석한다.
- 가능하면 knowledge cutoff 이후 평가 구간을 우선하되, 어려운 경우 limitation으로 명시한다.

## 4. 4개 에이전트 정의

## 4.1 Data Agent

### 역할
트레이딩 판단에 필요한 입력 데이터를 수집·정제·정렬·캐시한다.

### MVP 범위
- OHLCV 수집
- 기술팩터 계산
- 뉴스 메타데이터 수집
- 날짜/시간 정렬
- 결측/품질 플래그 처리
- `DailyMarketPacket` 생성

### 하지 않는 것 (MVP)
- 재무제표/실적/전사록 full integration
- 대규모 벡터DB 구축
- full RAG 검색 서비스

### 한 줄 정의
> **Data Agent는 판단하지 않고, 판단 가능한 입력 상태를 보장한다.**

---

## 4.2 Strategy Agent

### 역할
정량 신호와 뉴스 신호를 종합해 **무엇을 사고 / 줄이고 / 건너뛸지** 판단한다.

### 현재 확정된 내부 흐름

```text
Quant Prefilter
  -> Market Analyst
  -> News Analyst Lite
  -> General Synthesizer
  -> StrategyCard
```

### 각 블록의 의미

#### 1) Quant Prefilter
- DOW30 전체를 빠르게 점수화
- 5~8개 후보로 줄임
- 목적: LLM 호출 비용·지연·복잡도 제어

#### 2) Market Analyst
- 가격 / 기술팩터 기반 근거 해석
- “왜 이 종목이 shortlist에 들어왔는가”를 정리
- MVP에서는 수치 근거를 구조화된 evidence card로 바꾸는 역할이 핵심

#### 3) News Analyst Lite
- 최근 뉴스 헤드라인/요약을 보고 방향성과 근거를 생성
- MVP에서는 가볍고 짧은 입력만 사용
- full memory/refinement는 1차 확장으로 미룸

#### 4) General Synthesizer
- Quant, Market, News 결과를 합쳐 최종 thesis 생성
- action / evidence / contradiction / confidence를 정리

### Strategy Agent의 본질
> **Strategy Agent는 단일 예측기가 아니라, 단계적 판단 구조를 가진 상위 의사결정 계층이다.**

---

## 4.3 Risk Agent

### 역할
전략 판단을 그대로 주문으로 내보내지 않고, 위험 제약을 적용해 **실행 가능한 주문 계획**으로 바꾼다.

### MVP 범위
- position cap
- stop-loss
- turnover cap
- cash ratio 제어(간단 버전)

### 1차 확장
- volatility targeting
- regime gating
- sector exposure cap
- market stress / irrationality gate

### 한 줄 정의
> **Risk Agent는 전략을 반대하는 조직이 아니라, 전략을 실행 가능한 상태로 수정하는 조직이다.**

---

## 4.4 Backtest Agent

### 역할
OrderPlan을 실제 과거 구간에서 시뮬레이션하고, 성능과 실패 원인을 구조화해서 되돌린다.

### MVP 범위
- T+1 open 집행
- slippage + fee 반영
- walk-forward evaluation
- 기본 성능 지표 산출
- FailureCaseCard 발행

### 핵심 포인트
Backtest Agent는 단순 수익률 계산기가 아니다.

- 어떤 날짜/구간에서 실패했는지
- 어떤 가정이 깨졌는지
- 다음 실행에서 무엇을 바꿔야 하는지

를 구조화해서 Strategy 쪽으로 다시 보내는 **feedback engine**이다.

## 5. Artifact(카드) 중심 협업

에이전트들은 자유 채팅하지 않는다.  
우리는 **정해진 스키마를 가진 artifact**를 주고받는다.

### 기본 흐름

```text
Data Agent
  -> DailyMarketPacket
Strategy Agent
  -> StrategyCard
Risk Agent
  -> RiskCard + OrderPlan
Backtest Agent
  -> BacktestReport + FailureCaseCard
Orchestrator
  -> feedback 조건 충족 시 Strategy 재실행
```

### 왜 artifact가 핵심인가

- 역할 간 handoff가 명확해진다
- 실행 중간 상태를 저장/재현할 수 있다
- 발표/보고서에서 판단 경로를 설명할 수 있다
- hallucination cascade를 줄인다
- 나중에 ablation과 failure analysis를 하기 쉬워진다

---

## 6. 필수 Artifact 5종

| 카드 | 목적 | 누가 생성 | 누가 사용 |
|---|---|---|---|
| `DailyMarketPacket` | 오늘의 데이터 상태를 정렬해 전달 | Data Agent | Strategy Agent |
| `StrategyCard` | 후보 종목, thesis, evidence, contradiction 전달 | Strategy Agent | Risk Agent |
| `RiskCard` | 리스크 제약 적용 결과를 기록 | Risk Agent | Backtest / UI |
| `OrderPlan` | 실제 시뮬레이션 가능한 주문 계획 | Risk Agent | Backtest Agent |
| `BacktestReport` | 성능 지표와 결과 요약 | Backtest Agent | 팀 전체 |
| `FailureCaseCard` | 실패 원인과 다음 수정 제안 | Backtest Agent | Orchestrator / Strategy |

### 카드 설계 원칙

1. **짧아야 한다** — 읽는 주체가 다음 단계 agent이기 때문
2. **필수 필드가 고정돼야 한다** — 비교/디버깅 가능해야 하기 때문
3. **자연어와 수치가 함께 있어야 한다** — 설명 가능성과 재현성을 동시에 확보하기 위해
4. **버전 관리가 가능해야 한다** — SQLite artifact registry로 저장 가능해야 함

## 8. 실험은 제품의 일부다

우리는 단순히 “최종 수익률 하나”만 보는 프로젝트가 아니다.  
이 시스템은 **제품 + 실험 인프라**를 같이 만든다.

### 8.1 신호 스택 ablation

| 실험 | 구성 |
|---|---|
| S0 | Quant only |
| S1 | + Market Analyst |
| S2 | + News Analyst Lite |
| S3 | + General Synthesizer |
| S4 | + Memory / Notes |

### 8.2 리스크/실행 스택 ablation

| 실험 | 구성 |
|---|---|
| R0 | Risk 없음 |
| R1 | + position cap + stop-loss |
| R2 | + turnover / volatility control |
| R3 | + full risk agent |

### 8.3 결과 해석 원칙

- S 실험은 **신호 계층의 기여**를 본다.
- R 실험은 **리스크/실행 계층의 기여**를 본다.
- 둘을 섞어 한 줄로 해석하지 않는다.
- 발표에서는 “무엇을 추가했더니 어떤 지표가 좋아졌는가”를 말한다.

## 9. 참고논문 6편이 우리에게 주는 역할

| 논문 | 우리 프로젝트에서의 역할 |
|---|---|
| MetaGPT | 상위 Orchestrator, SOP, artifact, dependency, feedback loop |
| TradExpert | Strategy 내부 전문가 분업, Market/News 우선, shortlist 원칙 |
| AAPM | 정성-정량 결합, refined news, memory/notes, leakage awareness |
| AlphaGAT | Quant Prefilter / Factor Engine / 향후 allocator 설계 |
| AlphaAgent | Factor/Alpha Analyst 확장, anti-decay factor 탐색 원칙 |
| R&D-Agent-Quant | 오프라인 quant 연구 루프, factor-model co-optimization outer loop |

### 한 줄 해석

```text
상위 협업 구조는 MetaGPT식,
전략 내부 분업은 TradExpert식,
정성-정량 fusion은 AAPM식,
정량 코어 확장은 AlphaGAT/AlphaAgent식,
오프라인 연구 루프는 R&D-Agent-Quant식으로 가져간다.
```

## 10. 우리 팀이 직접 설계해야 하는 것 vs 재사용 가능한 것

## 10.1 직접 설계해야 하는 것

- 4개 agent 역할 정의
- artifact/card schema
- handoff 규칙
- Orchestrator
- feedback loop
- 누수 방지 정책
- 평가 프로토콜
- 실험 설계

## 10.2 재사용 가능한 것

- ML 모델 라이브러리
- LLM backend
- 데이터 수집 라이브러리
- DB / queue / scheduler
- 일부 백테스트 유틸리티
- 시각화 라이브러리

### 핵심 문장
> **우리가 직접 만들어야 하는 것은 “모델 자체”보다 “협업하는 금융 시스템의 계약과 구조”다.**

---

## 11. 이 프로젝트가 성공했다고 말할 수 있는 기준

## 11.1 시스템 성공 기준

- 4-agent runtime이 end-to-end로 실제 동작한다.
- 카드가 저장되고 재현 가능하다.
- failure card가 strategy 재실행에 실제 사용된다.

## 11.2 연구 성공 기준

- S0~S4, R0~R3 중 최소 핵심 실험이 재현 가능하다.
- 리스크/실행 계층과 신호 계층의 기여를 분리해서 설명할 수 있다.
- 최소 1개의 meaningful improvement를 보여준다.  
  (예: MDD 개선, Sharpe 개선, turnover 안정화, failure mode 감소)

## 11.3 발표 성공 기준

- “왜 이 판단이 나왔는지”를 카드 기반으로 보여줄 수 있다.
- “왜 이 구조를 택했는지”를 6편 논문과 연결해 설명할 수 있다.
- “무엇을 하지 않기로 했는지”도 명확히 말할 수 있다.

## 12. 팀원 모두가 외워야 할 7문장

1. **우리는 모델 하나가 아니라 협업형 트레이딩 시스템을 만든다.**
2. **4개 agent는 전부 거대 LLM일 필요가 없다.**
3. **MVP에서 가장 먼저 살릴 것은 Quant Prefilter + Market + News Lite다.**
4. **Fundamental은 후순위다.**
5. **전 종목 full LLM 분석은 금지한다.**
6. **핵심 기여는 최고 성능보다 SOP + artifact + feedback 설계다.**
7. **백테스트는 끝 단계가 아니라 다시 전략을 고치는 시작점이다.**
